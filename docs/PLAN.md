# MachineVoice — план реализации

Фоновое приложение, которое принимает события от AI-инструментов (первым источником будет Cursor), ставит ответы в очередь и озвучивает их.

## Принятые решения

| Тема | Решение |
|---|---|
| Стек | .NET 10: кроссплатформенное ядро + UI на Avalonia, платформенные адаптеры отдельно |
| UI | Сначала Avalonia. Если этап 0 провален, UI для macOS пишется на SwiftUI отдельным процессом поверх протокола управления; Avalonia остаётся для Windows и Linux |
| MAUI | Не используем: на macOS работает через Mac Catalyst (плохо с menu bar и `NSPanel`), не поддерживает Linux, требует workload, которого нет в Homebrew-сборке .NET |
| Связь UI и ядра | Только через протокол управления (`MachineVoice.Protocol`), даже когда UI живёт в одном процессе с ядром |
| TTS | Подключаемые движки: сначала системные голоса macOS, нейросетевые позже |
| Простой локальной модели | Настройка: через сколько без озвучивания выгрузить локальную модель из памяти. По умолчанию 10 минут. Само приложение остаётся запущенным |
| Предобработка | Правила по умолчанию, LLM-пересказ включается опционально |
| Режимы | «Авто», «По подтверждению» (тост с кнопкой «Слушать»), «Тихий» |
| Очередь | Переключатель в настройках: «Сначала новые» (LIFO, по умолчанию) или «По порядку» (FIFO). Звучащий ответ всегда дочитывается; в LIFO новый ответ становится следующим, а в режиме «По подтверждению» сразу заменяет тост, прежний ждёт за ним. Переключение сразу переставляет ждущие ответы |
| Что озвучивать | Короткий заголовок («Cursor, проект X») + полный ответ. Заголовок по настройке «Читать агента и проект»: «Всегда» (по умолчанию), «Никогда» или «При смене» — только если предыдущий прочитанный ответ был от другого агента или из другого проекта. Тема запроса пока не читается; для неё будет отдельная настройка |
| Источники | Пока только Cursor, архитектура расширяемая |
| Горячие клавиши | Пауза / продолжить, пропустить, открыть чат |
| Расширение CursorSpeaker | Не трогаем. Позже его заменит новый плагин-мост, если он понадобится |
| Старый хук `speak.sh` | Пользователь выключает вручную (`cursor-speaker.sh off`), иначе ответы будут читаться дважды |
| Дистрибуция | Пока для себя (ad-hoc подпись); публичный релиз возможен позже |

## Архитектура

```
Cursor hooks ──► integrations/cursor/hook.sh ──► Unix-сокет ──► Core
                          │ (демон недоступен)                   │
                          └──► inbox/ ──(при старте)────────────►┤
                                                                 ▼
                             нормализация → очередь → конвейер текста → ITtsEngine
                                                                 │
                                       App (Avalonia): menu bar, оверлей, тосты, настройки
```

Ядро не зависит от UI. Если оверлей на Avalonia окажется неудачным, ядро выносится в отдельный процесс, а UI для macOS пишется на SwiftUI поверх того же сокета.

### Протокол управления

Чтобы замена UI не затрагивала ядро, UI общается с ядром только через протокол управления: тот же контракт, что доступен по Unix-сокету.

- Команды: пауза, продолжить, пропустить, сменить режим, прослушать любой подготовленный ответ из очереди сразу (звучащий при этом пропускается), пропустить элемент из тоста, открыть чат, прочитать и изменить настройки, подключить / отключить источник и узнать его статус.
- События (подписка): состояние плеера, прогресс по словам, изменения очереди и истории, запрос подтверждения для режима «По подтверждению», изменения настроек.
- Формат: JSON-сообщения с полем `type` и версией протокола; события идут потоком по одному соединению (NDJSON).
- Avalonia-приложение использует in-process реализацию того же интерфейса и не обращается к внутренним классам ядра. Внешний клиент (SwiftUI, CLI) подключается через сокет и получает те же сообщения.
- Входящие события от источников (хуки Cursor) и протокол управления разделены по разным endpoint'ам, чтобы хук не мог управлять плеером.

### Структура репозитория

- `src/MachineVoice.Protocol`: DTO команд и событий протокола управления, версия протокола, интерфейс клиента. Без зависимостей от ядра и UI.
- `src/MachineVoice.Core`: модель событий, очередь, режимы, конвейер текста, интерфейсы `ITtsEngine`, `IHotkeyService`, `IAutostart`, `IQueuePolicy`, `ITextProcessor`.
- `src/MachineVoice.Platform.MacOS`: TTS (`say`, затем `AVSpeechSynthesizer`), горячие клавиши через Carbon, донастройка окна оверлея через Objective-C runtime, LaunchAgent.
- `src/MachineVoice.App`: Avalonia, иконка в menu bar, оверлей, окно настроек, хостинг ядра.
- `src/MachineVoice.Mcp`: MCP-сервер (stdio) поверх протокола управления. Зависит только от `MachineVoice.Protocol`.
- `integrations/cursor/`: `hook.sh` и установщик хуков.
- `tests/MachineVoice.Core.Tests`.

## Этапы

### Этап 0. Прототип рисков (1–2 дня, решение «.NET UI: да или нет»)

- Окно Avalonia, которое не забирает фокус, видно над полноэкранными приложениями и на всех Spaces (`collectionBehavior`, window level через P/Invoke).
- Глобальная горячая клавиша через Carbon `RegisterEventHotKey`, без разрешения Accessibility.
- Пауза и продолжение `say` через SIGSTOP / SIGCONT.
- `dotnet publish` с Native AOT → `.app` bundle с `LSUIElement` и ad-hoc подписью.

Прототип: `prototypes/Stage0` (Avalonia 12.1.3), сборка `.app`: `prototypes/Stage0/build-app.sh`.

Выводы прототипа:

- Окно Avalonia нельзя превратить в `NSPanel`: к моменту, когда окно доступно из C#, KVO уже подменил его класс на `NSKVONotifying_AvnWindow`, а флаг `NonactivatingPanel` у `NSWindow` сбрасывается.
- Вместо этого на окне вызывается приватный `_setPreventsActivation:` (его же использует `NSPanel`), окно не может стать key. С политикой активации `Accessory` показ оверлея, клики по нему и горячие клавиши не забирают фокус у активного приложения.
- Делегат приложения Avalonia активирует приложение при запуске, поэтому он отключён (`DisableAvaloniaAppDelegate`). Выход по завершению сеанса нужно будет обработать самостоятельно.
- Иконка в menu bar в Avalonia 12 создаётся только после `TrayIcon.SetIcons(application, ...)`; сам конструктор `TrayIcon` нативную иконку не создаёт.
- Пауза `say` через `SIGSTOP` не годится: замороженный процесс оставляет CoreAudio зацикленный буфер, и слоги повторяются. Пауза работает через `AVSpeechSynthesizer` (`pauseSpeakingAtBoundary:` по границе слова), поэтому он становится движком по умолчанию уже на этапе 4.
- Avalonia сбрасывает состояние окна при каждом `Show()`, поэтому `level`, `collectionBehavior` и запрет активации применяются заново после каждого показа.
- AOT-сборка из Homebrew .NET требует путей к OpenSSL и Brotli для линкера; с `-dead_strip_dylibs` бинарник не зависит от Homebrew. `.app` весит около 32 МБ.

Итог: критерии выполнены, UI остаётся на Avalonia.

Критерии «да» для Avalonia: оверлей не забирает фокус у активного приложения при показе и при клике по кнопкам, виден над полноэкранным приложением и на всех Spaces, иконка в menu bar работает без иконки в Dock, AOT-сборка запускается. Если оверлей не проходит критерии, UI для macOS переходит на SwiftUI, а остальные пункты прототипа (хоткеи, `say`, упаковка ядра) остаются в силе.

### Этап 1. Ядро

- `SpeechItem`: источник, проект, `conversationId`, `generationId`, тема, текст, время получения.
- Сервер на Unix-сокете в `~/Library/Application Support/MachineVoice/` с правами `0600`.
- Журнал входящих `inbox/`: принятое событие сначала записывается файлом и только потом подтверждается; файл удаляется, когда элемент попал в историю. При старте демон подбирает необработанные файлы, поэтому перезапуск не теряет ответы. Срок актуальности пока не ограничен.
- Дедупликация по `generationId`.
- Очередь с `IQueuePolicy` (сначала FIFO).
- Состояния плеера: тишина, говорит, пауза. Режимы «Авто», «По подтверждению», «Тихий».
- История и настройки хранятся в JSON.
- Протокол управления: in-process реализация и сервер на отдельном Unix-сокете с теми же сообщениями. Тест-клиент проверяет, что все команды и события работают через сокет.

### Этап 2. Адаптер Cursor

- `hook.sh` (bash + `curl --unix-socket`) пересылает сырой JSON хука с `source=cursor`; если демон недоступен, кладёт событие в `inbox/`. Скрипт не зависит от .NET и быстро завершается.
- Нормализация в ядре: `beforeSubmitPrompt` запоминает промпт как тему чата, `afterAgentResponse` даёт текст, `stop` со статусом `completed` ставит ответ в очередь. Новый промпт в чате убирает из очереди ещё не прочитанные ответы этого чата: пользователь уже ответил на них сам. Они попадают в историю как пропущенные; ответ, который звучит в этот момент, дочитывается.
- Установщик регистрирует хуки в `~/.cursor/hooks.json` и не трогает чужие записи (та же логика, что в `cursor-speaker.sh`). Установщик живёт в ядре (на .NET, без `jq`), чтобы его можно было вызвать из настроек через протокол управления: подключить, отключить, проверить статус.
- `hook.sh` копируется в `~/Library/Application Support/MachineVoice/`, и `hooks.json` ссылается на эту копию, а не на файл внутри `.app`: путь не меняется при переустановке или переносе приложения.

### Этап 3. Конвейер текста

- Цепочка `ITextProcessor`: разбор Markdown через Markdig, замена блока кода на «тут пример кода», сокращение путей и URL.
- Заголовок не входит в цепочку: движок добавляет его, когда ответ начинает звучать (`SpeechHeading`). Только тогда известно, какой ответ был прочитан перед ним: очередь LIFO, пропуски и «Слушать» меняют порядок. Для режима «При смене» сравниваются заголовки, то есть источник и проект.
- Опциональный LLM-пересказ через OpenAI-совместимый endpoint (подходит и Ollama). Шаг с тайм-аутом: если не уложился, используется результат правил.
- Ответ модели ограничен `max_tokens` (1024). Если модель упёрлась в лимит (`finish_reason: length`), пересказ обрезан на полуслове, и озвучивается результат правил.
- В системный промпт добавлен `/no_think`: гибридные модели (Qwen3) пропускают рассуждения, остальные модели переключатель игнорируют. Поля конкретных серверов (`think`, `chat_template_kwargs`) не используются, потому что строгие OpenAI-совместимые endpoint'ы отклоняют неизвестные поля.

### MCP-сервер

- `MachineVoice.Mcp` позволяет управлять MachineVoice обычными фразами из Cursor, Claude Code и других MCP-клиентов, без своей LLM в приложении.
- Транспорт stdio. Каждый вызов инструмента открывает своё соединение с `control.sock`, поэтому перезапуск MachineVoice не ломает сервер. Если MachineVoice не запущен, инструмент возвращает ошибку.
- Инструменты: `machinevoice_status`, `machinevoice_playback` (пауза, продолжить, пропустить), `machinevoice_set_mode`, `machinevoice_set_speed` (скорость чтения, действует сразу), `machinevoice_confirmation` (слушать или пропустить ответ в режиме «По подтверждению»), `machinevoice_set_summary` (включение пересказа, модель, тайм-аут).
- Подключение источников (правит `~/.cursor/hooks.json`), адрес LLM и ключ API через MCP не меняются: агент не должен перенаправлять, куда уходят ответы. Статус показывает только, задан ли ключ, и не включает текст ответов.
- Подключение в Cursor (`~/.cursor/mcp.json`) после `dotnet build`:

  ```json
  {
    "mcpServers": {
      "machinevoice": {
        "command": "dotnet",
        "args": ["<repo>/src/MachineVoice.Mcp/bin/Debug/net10.0/MachineVoice.Mcp.dll"]
      }
    }
  }
  ```

  Для другого сокета (например, в тестовом каталоге) добавить `"--socket", "<path>/control.sock"`. `dotnet run` не подходит: вывод сборки попадает в stdout и ломает протокол.
- Установщик MCP для Cursor (для кнопки в настройках, этап 5; реализован), по той же схеме, что установщик хуков из этапа 2:
  - `MachineVoice.Mcp` публикуется через Native AOT и кладётся внутрь `.app`. При подключении бинарник копируется в `~/Library/Application Support/MachineVoice/`, и `mcp.json` ссылается на эту копию: путь не меняется при переустановке или переносе приложения, и `dotnet` у пользователя не нужен.
  - Установщик живёт в ядре (на .NET) и правит только запись `machinevoice` в `~/.cursor/mcp.json`, не трогая чужие серверы и форматирование остальных записей. Файл, который не удалось разобрать, не перезаписывается: возвращается ошибка.
  - Статусы: подключён, не подключён, запись есть, но устарела (другой путь к бинарнику или копия старее, чем версия внутри `.app`).
  - Отдельные команды протокола управления: подключить MCP, отключить MCP, узнать статус. Это не источник ответов, поэтому команды не смешиваются с `connectSource`. Через сам MCP эти команды недоступны.

### Этап 4. TTS

- `ITtsEngine`: говорить, пауза, продолжить, стоп, события начала и окончания.
- Реализации по очереди: `AVSpeechSynthesizer` через interop (пауза по границе слова, прогресс по словам через делегат), позже нейросетевые HTTP-движки. Для их воспроизведения пауза через `SIGSTOP` у `afplay` не подходит (см. этап 0), нужен свой аудиовывод через `AVAudioPlayer` или AudioQueue.

Итоги: `AvSpeechEngine` в `src/MachineVoice.Platform.MacOS`. `AVSpeechSynthesizer` вызывает делегат только в главной очереди, на каком бы потоке его ни создали. В приложении её обслуживает `NSApplication`, а хост без UI должен отдать главный поток `MacMainLoop.Run`. Тесты с настоящим синтезатором (громкость 0) поэтому запускают тестовую сборку дочерним процессом.

Нейросетевой движок: Qwen3-TTS (`mlx-community/Qwen3-TTS-12Hz-1.7B-CustomVoice-bf16`, голос по умолчанию Ryan) через OpenAI-совместимый `/v1/audio/speech` из mlx-audio. Движок выбирается в настройках, раздел «Озвучка».

- `TtsSwitch` (ядро) направляет фразу в выбранный движок. Смена настройки действует со следующего ответа, текущий дочитывается тем же движком. Если Qwen падает посреди ответа (сервер не запустился, ошибка HTTP), остаток читает голос macOS, а индексы слов сдвигаются, чтобы прогресс в оверлее не прыгал назад. Если падает и голос macOS через звук, остаток читает `AvSpeechEngine` напрямую.
- Оба движка дают готовый звук, и его играет один плеер: `ChunkedAudioEngine` (ядро) с синтезатором фрагментов `IChunkSynthesizer`. Для Qwen это `QwenSynthesizer` (HTTP), для голоса macOS — `AvSpeechWriter` (`Platform.MacOS`): `AVSpeechSynthesizer.writeUtterance:toBufferCallback:toMarkerCallback:` пишет PCM в память вместо воспроизведения, а метки слов дают точное время каждого слова. Запись идёт примерно в 50 раз быстрее реального времени, буферы приходят в главной очереди (как делегат). `stopSpeakingAtBoundary:` запись не прерывает, поэтому следующая запись ждёт конца предыдущей, иначе буферы смешались бы. Блоки для обратных вызовов собираются вручную (`Interop/Blocks.cs`) как глобальные, чтобы среда выполнения их не копировала.
- Скорость двух видов:
  - скорость воспроизведения (`Tts.PlaybackRate`, 0,5–2): `AVAudioPlayer.rate` с `enableRate`, высота голоса не меняется. Действует сразу, в том числе посреди фразы. Меняется кнопками «−» / «+» в оверлее (шаг 0,1), в настройках, командой протокола `setPlaybackRate` и MCP-инструментом `machinevoice_set_speed`;
  - темп голоса macOS (`Tts.SystemVoice.Rate`, 0..1, 0,5 — обычный): `AVSpeechUtterance.rate`, синтезатор сам сокращает паузы, на сильном ускорении это звучит естественнее растяжения. Действует со следующего ответа. У Qwen3-TTS такого параметра нет: mlx-audio принимает `speed`, но для этой модели игнорирует его (и отключает пакетную генерацию), поэтому темп Qwen меняется только скоростью воспроизведения.
- `ChunkedAudioEngine` режет текст на предложения (`SpeechChunks`: первый фрагмент до 100 символов, остальные до 220) и синтезирует их по одному, начиная с того, что звучит, и не дальше двух фрагментов вперёд (голос macOS пишет весь ответ сразу: это быстро, и длительность ответа точная). На M4 Pro модель синтезирует примерно 0,8 с на секунду речи: отдельное предложение готово за ~5 с, и следующее успевает к концу текущего. Целиком ответ синтезировать нельзя: первая фраза ждала бы весь ответ.
- Параметры сэмплирования задаются явно (`temperature` 0.9, `top_k` 50, `top_p` 1.0, `repetition_penalty` 1.05), а `max_tokens` ограничен длиной фрагмента. С умолчаниями сервера (0.7, без штрафа за повторы) модель не останавливалась: на абзац в 15 с речи вернула 96 с звука.
- Воспроизведение через `AVAudioPlayer` (`AvAudioPlayer` в `Platform.MacOS`): пауза держит текущий фрагмент и не запускает следующий. Конец фрагмента опрашивается, делегат и главный поток не нужны. Прогресс по словам берётся из меток синтезатора, если они есть (голос macOS), иначе оценивается по позиции в фрагменте (Qwen). Позиция считается в секундах клипа, поэтому скорость воспроизведения прогресс не сбивает.
- Перемотка по времени: клик в точку прогресс-бара оверлея перематывает на этот момент ответа (команда протокола `seek`, позиция в секундах звука). Перемотка точная, без привязки к словам: звук может начаться с середины слова. Привязку к началу ближайшего слова или к паузе можно сделать по времени слов (оно уже есть) или по тишине в звуке, но пока её нет.
  - Позиция и длительность ответа приходят событием `player.position` (примерно 4 раза в секунду), и прогресс-бар идёт по времени, а не по словам. Длительность синтезированных фрагментов точная, остальных — оценка по числу символов в темпе уже синтезированных, поэтому у Qwen она уточняется по ходу чтения.
  - Перемотка внутри звучащего фрагмента только сдвигает плеер. Перемотка в другой фрагмент останавливает текущий, отменяет синтез фрагментов, которые больше не нужны, и синтезирует нужный (у Qwen это несколько секунд). Пауза при перемотке сохраняется.
  - Если ответ дочитывает запасной движок, время продолжается с места сбоя, а перемотка доступна только в его части. У `AvSpeechEngine` (последний запасной путь) времени нет: прогресс снова идёт по словам, перемотки нет.
- `MlxAudioServer`: если по локальному адресу никто не слушает, MachineVoice сам запускает `mlx_audio.server` (ищет его в `PATH`, `/usr/local/bin`, `/opt/homebrew/bin`, `~/.local/bin`), пишет его вывод в `tts-server.log` и останавливает после простоя (по умолчанию 10 минут, 0 — не останавливать) и при выходе. Чужой или удалённый сервер только используется. Сервер, оставшийся после падения MachineVoice, узнаётся по `tts-server.pid` и берётся под управление. Выбор Qwen в настройках сразу загружает модель в фоне: от холодного старта до первого слова около 4,5 с.
- Сквозной тест с настоящим сервером запускается отдельно: `MACHINEVOICE_QWEN_E2E=1 dotnet test --filter QwenEndToEndTests` (`MACHINEVOICE_QWEN_E2E_VOLUME=1`, чтобы слышать).

Второй нейросетевой движок: OmniVoice (`mlx-community/OmniVoice-bfloat16`, около 2 ГБ) через тот же mlx-audio. В сравнении сэмплов русского текста он оказался лучшим (OmniVoice 8, Silero 7,5, Piper 5, Qwen3-TTS 4,5, Chatterbox 2 из 10).

- Готовых голосов у OmniVoice нет. Без образца каждый запрос получает случайный голос, а seed не закрепляет голос: тот же seed на другом тексте даёт другой голос. Поэтому голос — это сохранённый образец (WAV и его текст), который каждый запрос клонирует (`ref_audio` и `ref_text` в `/v1/audio/speech`). Без образца голос менялся бы от предложения к предложению.
- Голоса создаются в настройках: «Новый голос» синтезирует короткую фразу (`VoiceStudio.SampleText`, около 7 с) случайным голосом и сразу её проигрывает. Понравившийся сохраняется под именем и сразу выбирается, неудачный заменяется следующим вариантом. Длинный образец замедляет каждое предложение: с образцом 15 с синтез шёл в 1,4 раза медленнее реального времени, без образца — в 0,6.
- Голоса хранятся в `voices/` в папке приложения (`{id}.wav` и `{id}.json` с именем и текстом), черновики — в `voices/drafts/`, они удаляются при запуске. Удаление выбранного голоса возвращает OmniVoice к случайному голосу. Команды протокола: `listVoices`, `createVoice` (выполняется вне цикла ядра, первый раз запускает сервер и загружает модель), `saveVoice`, `deleteVoice`.
- Встроенные голоса (`BuiltInVoices`): десять случайных голосов OmniVoice, отобранных на слух, и два голоса Silero (baya — «Байя», eugene — «Евгений»), которые OmniVoice клонирует по их записи той же фразы. Образцы лежат в `src/MachineVoice.Core/Tts/Voices/` и встраиваются в сборку как ресурсы. При запуске они записываются в `voices/builtin/`, потому что сервер читает образец из файла. В списке они идут первыми, id у них по имени (`laura`, `eugene`), удалить их нельзя (`deleteVoice` отвечает `invalidArgument`).
- Темп у OmniVoice не настраивается: mlx-audio оценивает длительность речи по тексту одинаково для всех голосов, `speed` эта модель не принимает. Язык текста (`Tts.OmniVoice.Language`, по умолчанию `ru`) в окне настроек пока не показывается.
- Qwen3-TTS и OmniVoice работают в одном процессе `mlx_audio.server` (`SharedSpeechServer`): сервер занят, пока занят любой из движков, и останавливается после самого длинного простоя из их настроек. Модель выключенного движка выгружается с сервера (`DELETE /v1/models`), чтобы обе модели не держали память; если движок выключили посреди ответа, модель выгружается после него. Выбранный движок получает настройки первым, чтобы сервер не остановился между уходом одного движка и приходом другого.
- Общая часть обоих движков (запуск сервера, фоновая загрузка модели, простой, выгрузка) — `MlxSynthesizer<TSettings>`, а `QwenSynthesizer` и `OmniVoiceSynthesizer` задают только запрос.
- Паузы и щелчки на стыках. Каждый запрос стоит около 2 с сверх самой речи: модель заново читает образец голоса. Поэтому короткая фраза синтезируется дольше, чем звучит («Готово!»: 2,2 с синтеза на 1,4 с звука), и несколько коротких фраз подряд съедали запас из двух готовых кусков. Кроме того, клип OmniVoice начинается со щелчка (первые 40 мс) и 0,4–0,9 с тишины, а кончается вместе с речью, без затухания. Что сделано: OmniVoice получает куски из нескольких предложений (`SpeechChunks.Split(pack: true)`, первый кусок до 100 знаков, остальные до 220). На ответе из 13 предложений синтез занял 22 с вместо 38,7 с при 48 с звука, а стыков стало 4 вместо 13. У каждого клипа щелчок глушится, тишина перед речью сокращается до 0,25 с, а края плавно нарастают и затухают (`WavFile.TrimStart`). Больший запас длины (`duration_s`) не помогает: модель ставит лишнее время в начало, а речь всё равно доходит до конца клипа. Сервер mlx-audio этот параметр и не принимает.
- Сквозной тест: `MACHINEVOICE_OMNIVOICE_E2E=1 dotnet test --filter OmniVoiceEndToEndTests`. На M4 Pro черновик голоса с запуском сервера и загрузкой модели с диска занял 8,9 с, две фразы клонированным голосом — 16,3 с вместе с воспроизведением.

### Этап 5. UI

- Иконка в menu bar: режим, очередь, история, настройки, выход. Клик по ответу в очереди читает его сразу.
- Оверлей-пилюля внизу экрана: источник, проект и тема, прогресс, кнопки пауза / пропустить / открыть чат. Команды «стоп» нет нигде: она была «пропустить и ждать», что путало с паузой и пропуском; «замолчать» — это пауза, «надолго» — тихий режим. Очередь ждёт «Продолжить» только после сбоя озвучивания, чтобы один сбой не прошёл по всей очереди.
- Тост для режима «По подтверждению» в том же оверлее: «Слушать», «Пропустить», «Открыть чат». Не зависит от «Не беспокоить» и не требует разрешений.
- В настройках раздел «Источники» с кнопкой «Подключить Cursor» / «Отключить Cursor» и статусом: подключён, не подключён, хуки есть, но устарели (например, сменился путь к `hook.sh`). Кнопка вызывает установщик из этапа 2. Если в `hooks.json` найден старый `speak.sh`, рядом показывается предупреждение, что ответы будут читаться дважды.
- В настройках кнопка «Подключить MCP к Cursor» / «Отключить MCP от Cursor» со статусом: подключён, не подключён, запись устарела. Кнопка вызывает установщик MCP (см. раздел «MCP-сервер»). После подключения рядом подсказка: если Cursor не подхватил сервер сам, его нужно включить в настройках MCP в Cursor или перезапустить Cursor.

Итоги: приложение в `src/MachineVoice.App`, сборка `.app` через `src/MachineVoice.App/build-app.sh` (Native AOT, `MachineVoice.Mcp` лежит рядом с основным бинарником в `Contents/MacOS`). Ядро работает в том же процессе, UI обращается к нему только через `IControlClient`, а состояние берёт из `ControlState` (в `MachineVoice.Protocol`): это снимок, который поддерживается в актуальном виде потоком событий.

- Оверлей и тост — одно окно. Оно показывается, пока ответ читается или ждёт подтверждения, и скрывается через 0,7 с тишины, чтобы не мигать между ответами.
- «Открыть чат» пока выводит Cursor на передний план (`open -b`), как и планировалось до появления плагина-моста.
- Окно настроек открывается само при первом запуске, пока Cursor не подключён. Для показа окна приложение активируется, оверлей и меню фокус не забирают.
- Установщик MCP (`CursorMcp`) правит `mcp.json` побайтно: остальные записи, комментарии, отступы, переводы строк и BOM остаются как были. Если ключ `machinevoice` встречается дважды, файл считается неоднозначным и не перезаписывается.
- Если бинарника MCP рядом с приложением нет (запуск через `dotnet run`), статус MCP — «недоступен», и кнопка подключения выключена.
- Второй экземпляр завершается сразу, если `control.sock` уже отвечает, иначе он перечитал бы `inbox/` и прочитал те же ответы ещё раз. SIGTERM и SIGINT закрывают ядро штатно.
- Аргументы `--root`, `--cursor-dir` и `--mcp` позволяют запускать приложение на тестовых каталогах, не трогая настоящие `~/.cursor` и данные MachineVoice. Из терминала агента окна видны, только если запускать через `open -n <.app> --args …`.

## Известные риски

- Поведение оверлея на macOS в Avalonia (проверяется на этапе 0): окно Avalonia — это `NSWindow`, а не `NSPanel`, поэтому стиль `.nonactivatingPanel` недоступен напрямую.
- Хуки Cursor не передают название чата: тема берётся из первого промпта или генерируется LLM.
- В .NET нет кроссплатформенного TTS и аудиовыхода: под каждую платформу пишется своя реализация.
- Homebrew-сборка .NET не ставит workload `macos`, поэтому доступ к AppKit идёт только через P/Invoke.
